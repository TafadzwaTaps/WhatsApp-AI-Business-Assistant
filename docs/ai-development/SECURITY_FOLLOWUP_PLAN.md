# Security follow-ups after Phase 4 — prioritised plan (2026-11-19)

Ordered by risk (impact times likelihood), with status. "Done" items are implemented and tested locally, uncommitted.

| # | Item | Risk | Status | Next step / notes |
|---|---|---|---|---|
| 1 | **Impersonation tokens on financial or irreversible operations** | High (insider or stolen support session can move money, redirect payouts, delete the account, change the owner email) | **Done**: new `require_not_impersonated` on order approve/cancel/refund/status, all payment-settings routes, delete-account, referral withdraw; owner email change refused for support sessions (billing was done in Phase 3) | Policy question still open: should a support session be read-only everywhere (also WhatsApp pushes such as `/orders/{id}/lifecycle`, broadcast, campaigns)? Recommended yes: add a global rule "impersonation = GET only" in `get_current_user` consumers with an allow-list |
| 2 | **Full refresh-token family rotation** | Medium (today a best-effort tripwire; a thief who refreshes first keeps their chain) | Planned | Add `fam` (family id) claim to the token pair at login; on refresh issue the same `fam`; keep per-process record `{fam: latest_jti}`; reuse of a non-latest `jti` after the 120 s grace revokes the family (insert `fam:<id>` into `revoked_tokens`, checked in `is_token_revoked`/`get_current_user`). Tests: thief-first, owner-first, two tabs, restart. No schema change (reuse `revoked_tokens` with `jti = "fam:<id>"`). Small, backward-compatible: old tokens without `fam` keep today's behaviour |
| 3 | **Remove the legacy WebSocket `?token=` URL form** | Medium (token in URLs and proxy logs) | Planned | Step 1: log each use with the client user-agent for a week; step 2 reject `?token=` once logs show zero use by the shipped frontend (inbox.js uses the first-frame form). Mobile app must be checked first |
| 4 | **Enforce a strong `SECRET_KEY` without invalidating sessions** | Medium | **Partly done**: warning when the key is under 32 characters (key kept); weak defaults were already replaced with a random key | Operator step, at a time a forced re-login is acceptable: set a 64-hex `SECRET_KEY` in Render. Optional code step afterwards: refuse to start with a key under 32 characters when `ENV=production` |
| 5 | **Insecure fallback secrets** | Medium | **Done** for the unsubscribe HMAC (now derived from the effective signing key; unchanged when `SECRET_KEY` is set) | Remaining: confirm `PAYMENT_WEBHOOK_SECRET`, `CRON_SECRET`, `WHATSAPP_APP_SECRET` are all set in Render (code already fails closed) |
| 6 | **Input validation on product and admin update endpoints** | Medium (tenant can write negative price/stock or arbitrary columns it owns; superadmin route has no allow-list) | Planned | `PATCH /products/{id}`: Pydantic model with bounds (price >= 0, stock >= -1 or None, name length, https image URL), unknown fields rejected only after a week in warn-only mode. `admin_update_business`: explicit allow-list of editable columns. Need the exact field list the dashboard sends (grep `saveProduct`) before enforcing |
| 7 | **Server-side image URL validation** | Low/Medium (tracking pixels, `data:` URLs, mixed content) | Planned | Reuse the `logo_url` rule from `_sanitize_site_settings` (https/http only, <= 600 chars, no whitespace or quotes) for `image_url` on products and `logo_url`; leave existing rows alone |
| 8 | **Production CORS restrictions** | Low (no credentials are sent, localhost origins only allow a local page to read responses a token would be needed for) | Planned | Add `ENV=production` handling: drop the three `localhost`/`127.0.0.1` defaults when `ENV=production`; replace `allow_headers=["*"]` with an explicit list. Required before cookie sessions (credentials need an explicit origin list) |
| 9 | **Consistent password policy** | Low/Medium | **Partly done**: reset now has the same 128 character and 72 byte limits as change-password | Remaining: one `check_password_strength` for signup, reset and change (today signup: 8 + letter + digit, reset: 8 + upper + lower + digit). Changing the rule rejects passwords some users already use only at the next change, never at login. Needs your decision on the single rule (suggest: 10+ characters, no composition rules, common-password denylist) |
| 10 | **Unguarded growth automations** | Low | Planned | `growth/cart_recovery.run_cart_recovery` and `growth/reengagement.run_reengagement` have no callers today; add `is_restricted(business_id)` at their top before they are wired to a scheduler |
| 11 | **Signup duplicate-email message discloses registered addresses** | Low (pre-existing UX trade-off) | Accepted | Changing it would give legitimate users no hint why signup failed; mitigated by signup abuse limits. Revisit if abuse is observed |
| 12 | **`python-jose` unfixed advisory (CVE-2026-85394) and `ecdsa` Minerva note** | Low here (needs an asymmetric key used as an HS256 secret; WaziBot pins `algorithms=["HS256"]` with a symmetric key; ECDSA signing unused) | Documented | Plan to migrate to PyJWT (a separate, approved dependency change) because `python-jose` is effectively unmaintained |
| 13 | **Cookie sessions** | See `COOKIE_AUTH_DESIGN.md` | Design only | Needs your decisions listed there |
| 14 | **CSP `'unsafe-inline'`** | Defence in depth | Scheduled for Phase 5 | Report-Only first, then incremental handler migration |

## Suggested order for the next implementation steps
1 (policy decision), 2, 6 and 7 together (shared dashboard checks), 3, 8 (before any cookie work), 9, 10, then 4 as an operator step.
