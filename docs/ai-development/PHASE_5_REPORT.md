## 1. Support sessions are read-only (approved decision 1)
Enforced in the backend (`core/auth.py get_current_user`), for every route that authenticates through it, not by hiding buttons:
- A "view as business" session may only use GET/HEAD/OPTIONS. Every write (POST, PUT, PATCH, DELETE) answers **403 "Support (view-as) sessions are read-only"**, whatever the route (so future routes are covered by default).
- GETs that export or download data, fetch invoices, call Stripe, or reach outbound services are refused too: `/debug/*`, `/me/test-whatsapp`, `/me/export`, `/me/data-export`, `/billing/connect*`, `/billing/invoices`, `/marketing/qr/download`, and any path containing `/export`, `/download` or `/invoice`. The one POST allowed is the dry-run `/campaigns/preview` (sends nothing).
- **Audit:** every blocked attempt is logged (`support.write_blocked`: who, business, method, path, IP, user agent); read access is logged once per (support user, business) per 10 minutes (`support.access`). A failed audit write is logged at WARNING and never lets the request through.
- Owner and superadmin sessions are unchanged (tested). The dashboard banner says "read-only support session"; the inbox no longer tries to mark chats read in a support session.
- **Exceptional writes** need a separate, explicitly authorised and audited workflow: **not built** (none requested).
Known limitation: the deny-list for GETs is a list plus path fragments, not an allow-list of readable routes; an allow-list is the stricter next step (needs a route inventory).

## 2. One password policy (approved decision 2)
`services/password_policy.py`, used by signup, password reset and password change (the old name `check_password_strength` delegates to it): 8 to 128 characters, spaces/Unicode/passphrases allowed, **no composition rules**, common passwords rejected (embedded list plus NFKC/casefold so full-width look-alikes cannot dodge it), trivial sequences rejected, a password built from the username, email name or business name rejected, **72 UTF-8 bytes maximum with a clear message (never truncated)**. Known-compromised check (Have I Been Pwned range API, only the first 5 hash characters are sent) is **built but OFF** (`PASSWORD_BREACH_CHECK=1` turns it on; 1 s timeout; fails open): switching on an external call is your decision. Existing hashes still verify and nobody is forced to change; the policy runs only when a password is set. Signup's minimum moved from 6 to 8 to match. Frontend (signup, reset page, profile password change, dashboard strength meter) no longer demands uppercase/digit/symbol and shows the 72-byte rule.
Residual: the reset route passes no account context (the token flow does not know the account before redeeming), so "contains your username" is checked at signup and change only.

## 6. Cookie authentication Stage 1 (implemented behind a flag that is OFF)
Your answers (2026-11-20): SameSite **Strict**; the Flutter app uses `Authorization: Bearer` only; `https://wazibothq.com` is the only browser origin. Built accordingly (details and rollback in `COOKIE_AUTH_DESIGN.md`):
- `COOKIE_AUTH_ENABLED` is **unset = OFF** (nothing in the repository sets it); read on every call so it can be switched off without a deploy. With it off nothing changes: no cookie is set or read (tested, including the opt-in header being ignored).
- Opt-in per request (`X-Auth-Mode: cookie`): login, signup and refresh set `__Host-wazi_at` (HttpOnly, Secure, Strict), `__Secure-wazi_rt` (HttpOnly, Secure, Strict, Path=/auth) and `__Host-wazi_csrf` (readable); the body then contains **no access or refresh token**. Clients that do not send the header (the mobile app) get exactly today's JSON.
- CSRF for cookie-authenticated writes and cookie refresh: double-submit token bound to the account plus same-origin check (Origin/Host, Sec-Fetch-Site); Bearer requests exempt; support tokens never accepted from cookies.
- Expiry, revocation, password-change invalidation, suspension and the refresh reuse tripwire all still apply to cookie sessions; logout revokes both cookie tokens and clears the cookies; the WebSocket accepts the cookie only with an allowed Origin; CORS still never allows credentials.
- 58 new tests (login, refresh, logout, revocation, expiry, password change, CSRF matrix, cross-origin/CORS, WebSocket, flag off); 20 protections mutation-verified. Independent security review: no critical/high; applied: same-site fetches refused on every cookie request, logout clears cookies only for a same-origin request that sent one, derived CSRF key, superadmin and support sessions Bearer-only, flag-off error shape unchanged. Known limit: the CSRF value is per account, not per session; behind a Host-rewriting proxy cookie writes fail closed until `COOKIE_AUTH_ALLOWED_ORIGINS` is set.
- **Not done on purpose:** the frontend (still localStorage + Bearer), enabling the flag anywhere, removing localStorage auth: each needs your separate approval.
