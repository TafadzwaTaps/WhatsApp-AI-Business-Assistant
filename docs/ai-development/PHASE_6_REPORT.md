## 6.4 WhatsApp compliance (the most important finding)
**Evidence (audit, code read; Meta rules from knowledge, not re-verified against today's docs):** every business-initiated send is free-form text; **none** checked WhatsApp's 24-hour customer-service window; no template sender exists; no WhatsApp opt-out exists (opt-out code is email only); window-closed errors (131047) were only logged. Worst paths: re-engagement (targets customers inactive 14+ days, raw POST, no error handling), broadcasts and "inactive" campaigns, booking reminders (retried on every scheduler run), cart recovery (a failed send was counted as sent and set the cooldown).
**Changes:**
- New `services/wa_window.py`: a batched, tenant-scoped lookup of each customer's last **inbound** message. A customer is skipped only when we **positively know** the last inbound message is more than 24 hours old. Unknown (no inbound row, lookup error) is **attempted**: the guard can only remove sends that are certain to fail, never block one that would work. It is a guard, not a workaround: nothing tries to reopen a window.
- Guard applied to: campaigns (and scheduled campaigns, which use the same service), `/broadcast`, re-engagement, cart recovery, booking reminders, payment reminders. New additive result keys: `skipped_window`, `window_note` (and a clear `first_error` when everyone is skipped). Replies to inbound messages (webhook AI replies, staff replies in the inbox) are **never** guarded (tested).
- Cart recovery now uses the real sender and **honours its result** (a failed send is no longer counted as sent, and no cooldown is set for a message that was not delivered).
**Effect to expect:** re-engagement to long-inactive customers now sends nothing (it could not succeed without a template); broadcasts and campaigns to older customers report them as skipped with the reason instead of failing in bulk.
**Needs your decision / approval (not changed):**
1. **Template sending** (utility templates for reminders and order updates, marketing templates for campaigns, re-engagement): a product feature plus Meta template approval; build with mocks first.
2. **WhatsApp opt-in/opt-out**: honour STOP/UNSUBSCRIBE on inbound and check it before marketing sends. Needs a storage decision (a customers column = schema change). `get_all_customer_phones` currently treats anyone who ever messaged as opted in to promotions, which is not strictly Meta-compliant.
3. **Graph API version**: `v18.0` is hard-coded in 12 places (`main.py:547`, `growth/reengagement.py:184`, `growth/cart_recovery.py:232`, `integrations/whatsapp.py:115,164,199`, `routes/admin_routes.py:198`, `routes/business_routes.py:340`, `services/whatsapp_catalog.py:76,115`, `services/whatsapp_service.py:269,334`). It is almost certainly past Meta's support window (Meta auto-upgrades such calls today). Plan: one `WA_GRAPH_VERSION` constant (env, default unchanged), then a tested bump after checking Meta's current changelog. Not done: a version bump changes behaviour and needs your approval.
4. The shared-number fallback (invalid phone ID sends from the shared WaziBot number) exposes one quality rating to every tenant: decide whether to keep it.
5. Re-engagement still uses a raw POST with no retry or pause flag and sets no cooldown on failure; routing it through `send_whatsapp` is a small follow-up (the window guard removes its main failure cause). Scheduled campaigns still store no failure reason (needs a column); handoff notifications to an owner who never messaged the number, and staff-reply 131047 surfacing, are not changed.

## 6.1 AI conversation quality
**Evidence (code trace, nothing executed):** deterministic keyword/regex chain; the LLM only paraphrases confirmations; no invented prices or products (names and prices come from the database).
**Changes (all targeted, each tested):** `_qty` no longer reads measurements and sizes as quantities ("Fanta 500ml", "size 10 sneakers", "2 x 1.5l coke" are 1, 1 and 2); common non-name phrases ("I'm hungry", "it's late") are no longer saved as the customer's name; handoff patterns no longer escalate "can you call me when it's ready" or "I would like some help choosing" (explicit requests for a person still do); the prompt-injection guard no longer refuses "what are your rules on returns?" while "what are your system prompt / hidden rules / instructions" are still blocked.
**Needs your decision (not changed, from the audit, ranked):** abandoned checkout state never expires and carts never expire (stale state answers "choose how to pay" days later); cart prices are copied at add time and trusted at checkout (price changes are not picked up: touches the payment path); `_intent` substring collisions (`"hi "` inside "sushi", `"remove "` in "remove onions"); `cancel` is too blunt and the "yes, cancel" confirmation handler was not found; fuzzy product match without a confirmation; language detection never returns to English; shared-phone memory ("the usual" can reorder another person's items); order-preview "no" is not handled; a failed cart save still says "Added!"; **"where is my order" is deliberately treated as a refund/dispute phrase today (exact-match set and a test built around it): I tried treating it as a status question, found the behaviour inconsistent with the existing design, and reverted it: this is a product decision**; missing medical/legal phrases and frustration phrases for handoff.

## Reviews (independent security and QA, both read-only)
**Security: no critical or high.** Applied: only plain phone-number-shaped values reach the query filter (anything else is "unknown": attempted, never suppressed); re-engagement and cart recovery look the window up once per run instead of once per customer; "call the manager / contact the owner / call a supervisor" escalate again after my narrowing of the handoff patterns; unknown payment-method labels contain only plain characters; a malformed cookie value can no longer break the Stage 2 client. **Accepted and documented:** cart recovery's raw-HTTP fallback is unchanged (reached only when the shared sender is missing) and a persistent non-window failure retries each run (needs a failure cap: follow-up); "what are your rules / guidelines" is now allowed on purpose (generic policy question; "what are your system prompt / instructions / hidden rules" remain blocked); "I would like assistance" without "from a person" no longer hands off (deliberate trade-off: it is an AI question); payment-reminder lookups are still per reminder (low volume); the `messages.created_at` column type should be confirmed `timestamptz`.
**QA:** found that the dashboard ignored the new `skipped_window`/`window_note` keys and would have shown "Sent 0" as a green success (fixed: the broadcast and campaign screens now explain the skipped customers, show an error style and toast when nobody could be reached, and the broadcast "reached customers" button excludes skipped numbers via a new `skipped_window_numbers` list); found that my measurement rule would have turned "3 kg rice" into one unit (fixed: a weight or volume written first with a small number stays a quantity; sizes after the product name and ml/cm/oz/inch values never are); an `email_changes_are_rate_limited` failure it saw was interference from my own mutation-testing scripts running at the same time (re-run clean three times in a row). **Still open from QA:** scheduled campaigns that skip everyone end as "failed" with no stored reason (needs a column: your decision).
